# Changelog

All notable changes to the public Project Init package are documented here. There are **no verified earlier public releases**; the numbers reflect the local development lineage.

## Unreleased — licensing and GitHub preview distribution

### Fixed
- Windows command discovery supports native executables such as `codex.exe` without requiring a `.cmd` shim. Batch dispatch preserves the selected absolute `.cmd`/`.bat` path, quotes ordinary arguments, and rejects unsafe shell expansion/control characters.
- Added Windows regressions for executable discovery, PATH precedence, batch paths and arguments containing spaces, conflicting working-directory shims, and unsafe argument rejection. Command windows stay hidden during execution.

### Changed
- Added the unmodified Apache License 2.0 and an attribution/provenance NOTICE covering original Project Init, legacy v1, and bundled Lean Kit code with maintainer authorization.
- Updated package and lockfile SPDX metadata; the package stays `private: true` to explicitly prevent accidental npm publication while supporting reviewed GitHub release tarballs.
- Updated release checks, documentation, and contributor terms. GitHub releases still require an explicitly created version tag; production acceptance remains pending.
- Rewrote the README for a shorter, task-first path: what Project Init does, install, set up, daily use, Factory, and what the gate does and does not prove. Dashboard serving steps now live only in the dashboard docs.
- Added `docs/ROADMAP-2.2.md`, a proposed, prioritized plan for domain packs that keeps Project Init a personal development harness: pack mechanism, first-class BMAD, PowerShell/M365 pack, hooks, model routing, evals, local-first CI, GitHub pack, supply chain, `learn` feedback loop, web/GDPR pack, gated deployment, issue intake, and later tenant configuration as code. Nothing in it is implemented.

- Added `AGENTS.md` (imported by `CLAUDE.md`) with the rules for coding agents working on this repository, and Spec Kit feature specs `specs/001`–`specs/014` for every 2.2 roadmap phase, with build order in `specs/README.md`.

### Fixed (documentation)
- NOTICE listed the bundled Factory on the same line as Lean Kit because of a literal `\n`.

## [2.1.0-preview.16] — 2026-10-26 (agents follow Project Init everywhere; Codex or Claude orchestrates)

### Fixed
- `status` no longer reports success in a linked Git worktree that has no Project Init state of its own while another worktree of the same repository is initialized. It exits 1 with `blocked` (`linked-worktree-without-state`), names the initialized checkout and its Factory board, and lists the allowed next steps. Previously an agent session in such a worktree (for example a Claude Code session worktree, which receives none of the untracked `.project-init/`, `specs/`, `.specify/` or skill folders) saw `initialized: false`, exit 0, and worked outside every gate. Worktrees that own a native feature and registered Factory worktrees are not blocked.
- Skills generated by an earlier Project Init are updated in place by `wire` instead of being reported as conflicts, so an update reaches existing installations. Hand-written skills remain protected.

### Added
- `wire --scope user` maintains one marked Project Init rules block in `~/.claude/CLAUDE.md` and in Codex's `AGENTS.md` (`CODEX_HOME` respected). Every agent session, in every worktree, is told to run `status` first, obey `blocked`, work spec-first, and route work through the Factory job. Only the marked block is managed; the user's own instructions are preserved.
- `init --apply` from the CLI offers the user-scope rules and skills after the project skills, so a fresh install works without manual wiring. Library callers never touch a real user profile.
- The Factory orchestrator is selectable: `factory --orchestrator claude|codex` and `init --orchestrator ...` record it as `orchestrator` in the Factory config (default `claude`). Codex receives a `factory` orchestrator skill; both orchestrator skills refuse to act when the other agent is configured, and only the configured orchestrator writes the board. `board.py status` prints the orchestrator.
- `claude_worker.py` runs Claude Code headless (`claude -p`, prompt on stdin) as the Claude worker (`build`, `fix`) and runs the bundled Factory agents (`agent <slug> factory-<name> [round]`) for a Codex orchestrator. Claude worker runs leave the same process receipt as Codex runs; integration records them as `claude-process`, and `execution factory` verifies them and rejects a newer unintegrated Claude run. Interactive Claude commits stay `interactive-commit` and claim no process.
- Existing Factory configs gain the new `orchestrator` and `claude` settings on update without overwriting chosen values.

### Changed
- All skill preambles state that a worker reports through its job files and only the configured orchestrator writes the board.

## [2.1.0-preview.15] — 2026-10-25 (feature preparation and Factory evidence)

### Added
- Built-in `prepare` discovers the active native feature, existing task IDs and real package checks, preserves custom mappings, and registers the baseline only after check/mapping/design preparation is complete. Explicit feature/file selections survive normal follow-up calls.
- Existing-feature preparation and project-local Project Init skill updates are connected to normal guided init and the Claude/Codex start, plan, build and verify instructions. New sessions carry native feature/task/worktree context.
- Factory records actual Codex process outcomes and Git integrations, binds each job to its approved starting baseline/native scope, and verifies the integrated source through `execution factory`.
- `execution existing` supports independently reviewed already implemented code without fabricating an implementation run or changing code solely to satisfy a receipt gate.
- Check discovery reports application CI configuration separately from verified runs and branch-rule enforcement. The tool's own CI now provisions Python and includes preparation, evidence and dashboard regression suites.

### Fixed
- Init preview is read-only, including a missing target directory. Tooling readiness no longer claims feature or acceptance readiness.
- Factory apply safely creates a valid empty board only if absent. Existing job history is preserved; missing, invalid, denied and disconnected dashboard states have distinct messages.
- Failed check launches invalidate older passing results, checks that modify source cannot pass, and check working directories cannot cross into another Git worktree.
- Registered nested worktrees and Factory runtime updates no longer stale the parent source fingerprint. Git-tracked vendored source remains covered.
- Worktree registration, execution receipts and board locations resolve real filesystem identity across Windows short/long path aliases while retaining different-checkout and unsafe-link rejection.
- Factory records baseline-bound LF/CRLF checkout representations for native UTF-8 Markdown/text specifications without rewriting source or approval. Actual content changes and stale raw-byte source evidence remain blocked.
- Missing native requirement mappings, partial preparation, stale/failed worker attempts, wrong-feature integration, altered logs and out-of-scope filenames fail closed.

### Compatibility and validation limits
- Existing native specifications, user checks, requirement IDs, valid approvals, board history and unmanaged source are preserved. Skill upgrades use the existing explicit backup flow.
- Legacy execution receipts without baseline/scope binding are not upgraded into invented evidence. Existing code can be reviewed through the explicit existing-code path; older Factory jobs remain visible but cannot acquire fabricated start-time history.
- Regression fixtures exercise synthetic workers/installers and real local Git/check processes. Live authenticated Codex/Claude operation and Windows browser/workstation acceptance remain separate.
- No Trace application changes, automatic merge, release or deployment are included.

## [2.1.0-preview.14] — 2026-10-25 (ECC capability fallback)

### Fixed
- Stable Codex CLI releases that do not expose `codex plugin ...` are no longer treated as broken or repeatedly reinstalled.
- Project Init now selects the ECC install channel independently for Claude and Codex instead of requiring both harnesses to support ECC's native plugin lifecycle.
- The obsolete "repair Codex plugin inventory API" loop has been removed.
- ECC execution still uses the normalized Windows native Codex runtime for later shell-less Factory workers.

### ECC channel selection
- Claude: native ECC plugin when Claude Code exposes plugin inventory APIs; otherwise ECC's supported project-local managed adapter.
- Codex: native ECC marketplace/plugin lifecycle when available; otherwise ECC's supported `--profile core --target codex` managed home adapter.
- Custom `CODEX_HOME`: when native Codex plugin APIs are unavailable, Project Init uses ECC's documented legacy Codex sync compatibility path because that path explicitly honors `CODEX_HOME`.
- Existing ECC ownership state pins the previously selected managed/legacy channel to avoid stacking install methods.

### Added
- Bootstrap preview and confirmation now show the selected ECC channel for each worker.
- Added regressions for the real mixed case: Claude native plugin + Codex managed fallback.
- Added regression coverage that custom `CODEX_HOME` selects ECC legacy sync instead of installing into the wrong default `.codex` directory.

### Compatibility
- Existing uv, Spec Kit, Codex/Claude CLI authentication and prior verified bootstrap steps are reused.
- No cleanup is required after preview.13's failed Codex plugin-capability repair attempt; update Project Init and rerun the same guided bootstrap.

## [2.1.0-preview.13] — 2026-10-25 (Windows agent runtime normalization)

### Fixed
- Fixed a Windows runtime mismatch where `codex --version` succeeded in PowerShell through npm's `codex.cmd` shim, but ECC 2.2.3 failed with `Codex CLI is not installed or codex is not on PATH` because its Codex plugin adapter uses `execFile(..., shell:false)`.
- Project Init now resolves the native `codex.exe` payload shipped by the official `@openai/codex` platform package and prepends that native directory to the environment passed to ECC.
- Preserves the npm-managed Codex environment markers when bypassing the JavaScript launcher.
- Guided and advanced ECC execution now use the same normalized vendor environment.
- The bundled Factory Codex worker now resolves the native Windows Codex payload as well, rather than relying only on npm shell shims.

### Added
- Project Init preflights the Codex and Claude plugin inventory commands required by ECC before starting ECC.
- Added a Windows regression that launches `codex` with `shell:false` from the normalized vendor environment, directly reproducing the execution style that previously failed.

### Compatibility
- Existing Codex/Claude authentication and installed Spec Kit state are reused.
- No Trace cleanup is required after the preview.12 ECC failure; update Project Init and resume the same guided bootstrap.

## [2.1.0-preview.12] — 2026-10-25 (ECC dual-harness fix)

## [2.1.0-preview.10] — 2026-10-25 (agent CLI readiness candidate)

### Fixed
- Spec Kit initialization now uses its official `--ignore-agent-tools` option because Project Init owns Codex/Claude runtime readiness.
- Guided Spec Kit setup no longer exposes a second nested confirmation that users cannot answer; Project Init's own Y/N approval authorizes the safe existing-repo preserve-merge and raw vendor output remains in the install log.
- Failed/stopped bootstrap summaries refresh prerequisite state, so already-installed tools no longer appear as still missing.

### Added

### Compatibility
- The preview.9 guided prerequisite installer and preview.8 parallel isolated-worktree Factory model remain unchanged.
- Existing authenticated CLIs are reused and are not reinstalled.

## [2.1.0-preview.8] — 2026-10-25 (parallel worktree Factory candidate)

### Changed
- Removed the fixed Codex=backend / Claude=frontend Factory ownership model.
- Codex and Claude are now general implementation workers; Factory assigns independent work units by dependency and file boundaries.
- Factory creates isolated Codex, Claude and integration Git worktrees from the same committed base so workers can execute concurrently without sharing a checkout.
- Reviews run against the integrated result and findings route by actual worker ownership: `[CODEX]`, `[CLAUDE]`, or `[INTEGRATION]`.

### Added
- Added a cross-platform Python worktree manager for create/reuse, worker sync and deterministic integration.
- Added generic Codex `factory-worker` and integrated-result `factory-audit` skills.
- Added a generic Codex worker bridge that runs inside the Codex worktree and commits only that worker's changes.
- Added real-Git regression coverage that creates three distinct worktrees/branches.

### Migration
- Unmodified Project Init-managed `backend-factory`, `backend-audit`, and `codex_backend.sh` files are removed during Factory upgrade.
- Customized legacy files are preserved instead of deleted.
- Legacy Factory config is migrated to the parallel-worktree schema while retaining user settings such as test commands and Codex arguments.
