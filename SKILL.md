# Project Init 2.1

Read `README.md` and `docs/INVARIANTS.md`. This skill orchestrates the process; the chosen framework owns its own PRD, specifications, architecture decisions and implementation tasks. Never regenerate a competing PRD or silently switch methodologies.

1. For the normal software-factory workflow, start or resume with `project-init init --project .`. It inspects the real repository, preserves existing `AGENTS.md`, `CLAUDE.md`, source and unrelated dirty work, and returns one combined Factory bootstrap plan. Re-run the same command with `--apply` only after reviewing that plan.
2. The Factory profile uses Spec Kit as the single planning/spec owner, ECC as the shared engineering/security/testing toolbox, and the bundled Factory as a parallel isolated-worktree execution/review loop for Codex and Claude. The lower-level `recommend`, `select`, `install`, `ecc`, `factory`, and `wire` commands are advanced controls, not required setup steps. If an existing repository already has another methodology, stop rather than creating a competing Spec Kit source of truth.
3. Reuse the existing native feature, requirements and remaining task IDs. Run `project-init prepare --project .` before planning, building or verifying; apply preparation when the requested work authorizes it. Resolve check/mapping gaps from actual project scripts and tests using `--mapping`; this is agent work, not a requirement that the user write JSON. Use Spec Kit to create missing native artifacts only when the feature genuinely lacks them. Preserve the selected worktree, branch and actual Factory slug across sessions. `project-init handoff` is an instruction handoff, not proof a worker ran.
4. For UI projects, produce explicit high-fidelity `ui-design.json` screens with real navigation, labels, typography, colors, interactions, states and responsive variants; render `review.html` for human review. Use actual mockup PNGs as immutable-by-approval reference evidence.
5. Finish the actual check configuration, requirement mappings and applicable UI references before preparation registers the native baseline. Obtain independent review and **actual** user approval of that baseline. Report tooling readiness, feature preparation, approval and verified implementation separately. Never fabricate reviewers or acceptance.
6. Execute bounded implementation work using the appropriate native workflow. Use Factory when isolation, task routing and coordinated review are useful; do not create a replacement job or PR just because an existing PR needs fixes. `project-init run --execute` is a **Codex-only** local foreground runner. For a real Factory job, import its observed execution/integration chain with `execution factory` and continue verification in the returned integration worktree. Claude's interactive work is represented as observed Git integration, never an invented unattended Claude run. Read `docs/FACTORY-EVIDENCE.md` for the exact contract.
7. Run real configured checks with `verify --execute`, record actual independent source and semantic review, run applicable `visual compare`, then `guard`. For already implemented work without usable execution history, use `execution existing` after current checks/review; it records verification only and never claims implementation ran. Distinguish application CI configuration from successful CI runs and enforcement. Any stale reference PNG or source change invalidates cached acceptance evidence.
8. Built-in Lean Kit: `project-init lean --project . --input docs/REPORT.md --out .project-init/lean/REPORT.html --execute`; it renders reports and boards, not product screens. Do not request a separate Lean Kit installation or unsupported token-savings claims.
9. Return true status, blockers, test evidence, diff and rollback approach. Green gate permits *human release review*, not deployment. No automatic Git commit, push, merge, credentials, production changes, or API-key additions.

Guided `init --apply` installs or updates the project-local menus with a reviewed backup plan for conflicts. They are discoverable as `$project-init-*` in Codex and `/project-init-*` in Claude after reloading. `wire` remains an advanced installation control. Claude `/project-init:design` namespace requires loading the optional generated plugin using `claude --plugin-dir`; it is not implied by project skill installation. Read `docs/FEATURE-PREPARATION.md` for existing-work preparation and `docs/INSTALL.md` for installation details.
