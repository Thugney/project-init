# Feature specification: Work intake from issues

**Feature:** `013-issue-intake`
**Roadmap:** Phase 13 · Issue #59
**Status:** ready for build approval
**Depends on:** `008-github-pack` (GitHub access). Before building, re-read this spec against the code as built and report any mismatch instead of improvising.

## Summary

Today work starts only when the maintainer prompts an agent. Intake turns labelled GitHub issues and Dependabot pull requests into **proposed** Factory jobs. The orchestrator drafts the native spec change for each and stops for approval; nothing is built without it. Project Init stays a command the maintainer (or their own scheduler) runs; it does not become a background service.

## User stories

### US1 — Labelled issues become proposals (P1)

When I run intake, each open issue with the configured label (default `agent-ready`) and no existing job becomes a proposed job with a drafted native spec change, waiting for my approval.

### US2 — Dependabot pull requests become verification proposals (P2)

Each open Dependabot pull request becomes a proposed verification job: run checks on the PR branch, dependency review (spec 009), and a summary for my decision.

### US3 — Production errors can reach the same flow (P3)

Documentation shows how an error-tracking service's GitHub integration creates labelled issues, which then flow through US1.

## Functional requirements

- **FR-001 Command.** `project-init intake --project .` lists candidates (read-only). `--apply` registers proposed jobs. Running it again is idempotent: an issue or pull request already linked to a job is skipped.
- **FR-002 Proposed stage.** The Factory board gains a `proposed` stage. A proposed job has its source (`issue:<number>` or `dependabot:<pr>`), title, link and the drafted spec change; it cannot move to `building` without an approval recorded by the maintainer.
- **FR-003 Drafting.** For issues, the orchestrator drafts the change in the project's native methodology (Spec Kit feature or BMAD story) without creating a competing spec; the draft is marked as unapproved.
- **FR-004 Approval.** `/factory approve-proposal <slug>` (and Codex equivalent) records the maintainer's approval and moves the job to `spec`; `/factory reject-proposal <slug> <reason>` closes it and comments the reason on the issue only if configured.
- **FR-005 Data boundary.** Intake reads issue title, body and labels only. Issues must be written from the code perspective; documentation and the issue template generated by 008 state that personal data does not belong in issues. Intake does not copy issue text containing configured sensitive patterns into job files; it links instead.
- **FR-006 Scheduling stays outside.** Intake runs only when invoked. Documentation shows how to run it from the maintainer's own scheduler if wanted; Project Init ships no daemon.
- **FR-007 Limits.** At most a configured number of proposals per run (default 5) to bound model usage.

## Success criteria

- **SC-001** A labelled issue produces a proposed job that waits for approval; an unlabelled issue produces nothing (recorded API fixtures).
- **SC-002** Re-running intake creates no duplicates.
- **SC-003** A proposed job cannot reach `building` without a recorded approval (test).
